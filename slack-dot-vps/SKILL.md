# 在 Linux VPS 上通过 Slack 网页通知 Dot

目标是让自建程序在服务器上以用户已登录的 Slack 网页身份发私信，并由 Dot 在原消息下回应。此前用 User Token 调用 chat.postMessage 可以送达，私信和频道提及都未观察到自动回复；通过网页输入框发送则在 Mac 和 Linux 上分别成功。区分发送、送达与回复，沿用已经验证的网页路径。

## 换服务器

- 根据本次请求确认目标 SSH 主机、管理账号和已核对的主机指纹。旧机器只作为参照。检查发行版、CPU 架构、磁盘、内存和已有安装；复用兼容组件。东京的已验证组合是 Ubuntu 24.04 x86_64、官方 Google Chrome Stable、Python venv 和 Playwright。其他架构先核对 Chromium 和 Playwright 的支持。
- 为浏览器使用专门的普通 Linux 用户。浏览器配置目录仅该用户可读写，venv 安装 playwright。用系统 Chrome 时指定可执行文件，保留 Chromium 沙盒。不要把 Slack 令牌、Cookie、登录配置或 SSH 私钥放进项目、技能、聊天或日志。已有的 Dot 和 Slack 工作区绑定可以沿用。
- 从旧机器迁移时，优先让用户在新机器登录一次。待新机通过验收后，按用户指定的时机切换发送目标；若原来有队列或常驻任务，同一提醒只交给一个发送端。保留旧机与无关的 VPS 服务，清理或退役旧部署另按用户要求执行。

## 首次登录或登录过期

1. 用 Xvfb 创建临时显示，配置 Xauthority 并禁用 X11 的 TCP 监听。在该显示上以专用用户启动 Chrome，打开 Slack 登录页，指定专用的 --user-data-dir。记下用户、Chrome 路径、配置目录和所用启动参数。有可用的密钥环时保持一致；原部署使用 --password-store=basic，该配置目录应按登录凭据保护。
2. 将临时显示接到 x11vnc 和 noVNC/websockify，服务端仅监听回环地址。确认绑定后，用 SSH 本地转发把 Mac 的回环端口接到远端 noVNC，端口按当前机器选取。例如：
   `ssh -N -L 127.0.0.1:16083:127.0.0.1:16083 <已确认的SSH主机>`
3. 让用户在 Mac 打开 `http://127.0.0.1:16083/vnc.html?autoconnect=1&resize=scale`（按实际端口替换），亲自在远端 Chrome 中登录和完成验证。出现 xdg-open 提示时留在网页版。核对已进入正确工作区，确认 Dot 的私聊链接和身份，避开通用 ChatGPT 应用与频道。
4. 正常退出此次有窗口浏览器，等进程释放配置目录。若遇 ProcessSingleton，核实持锁的主机、用户及进程；不要删除仍在使用的锁。无窗口端用相同用户、同一配置目录、Chrome 路径及兼容启动参数。登录过期时保留待办，提示用户通过临时界面重新登录。

## 无窗口发送与验收

- 使用 Playwright 的 `chromium.launch_persistent_context(profile, executable_path=chrome, headless=True, chromium_sandbox=True)`。按主机情况沿用 `--disable-dev-shm-usage` 等参数。每个配置目录仅允许一个浏览器实例。
- 在 Linux 进程中打开已确认的 Dot 私聊链接。从可访问性树识别私聊主输入框；输入框的无障碍名称可能是 `Message to <Dot name>`，以实际工作区、收件人和界面语言为准。等待页面加载；资源有限的 VPS 可能需要较长的加载时间。确认收件人后填入用户授权的消息，按一次 Enter。
- 验收时生成全新的随机编号，例如 `DOT-LINUX-` 加随机十六进制串；要求 Dot 在原消息回复串只回复编号。用户在观察期先不另行提醒。保存父消息稳定链接或时间戳，打开该条回复串，核对回复作者为目标 Dot 且正文与编号完全一致。默认可观察约三分钟，已有回复则提前结束。用户只要求配置时，不自行向 Dot 发送业务任务。
- 若发送后超时、页面重载或 SSH 断开，先在原私聊按该编号核查，防止重复投递。父消息可见但无回复时，报告已送达、唤醒未验证。若要验收写回 Codex，再到指定主机和会话核对新一轮内容。
- 验收后关闭测试浏览器、本次临时虚拟桌面和 SSH 登录隧道。保留专用配置以供下次无窗口发送。交付时说明部署主机、配置位置、原消息链接或实际阻塞点，以及是否有常驻进程。单次验证不会自动建立监控或补发任务。
